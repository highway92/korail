# 실사이트 화면 관찰 기록

2026-10-01, 공개 코레일 웹 화면을 Chrome/Playwright에서 직접 조회했다. 첨부 스크린샷은 흐름 설명 자료이며 DOM selector의 근거로 취급하지 않는다.

## 확인한 부분

- 일반 조회 주소: `https://www.korail.com/ticket/search/general`
- 조회 결과 주소: `https://www.korail.com/ticket/search/list`
- 출발역/도착역 선택 link, 역명 link, `txtGoStart`, `txtGoEnd` 입력값.
- `출발일` link → 날짜 선택 dialog → `.datepicker`의 `p.date`로 월 구분 → 날짜 link → `적용`.
- 미래 날짜 선택 후 `00시 이후 출발` 표시. `#startDate`에서 적용값 확인.
- `열차 조회` button 클릭 뒤 결과 주소 이동.
- 결과 조건: `#labelstart`, `#labelend`, `#startDate`.
- 결과 영역: `.tckWrap > ul`. 빈 결과는 `해당 스케줄에 운행하는 열차가 없습니다.` 문구.
- 공개 홍보 dialog의 `창닫기`만 처리. 미확인 확인창을 일괄 승인하지 않는다.

## 남은 확인

자동화 Chrome에서 10월 9일 용산→정읍과 10월 2일 서울→부산을 조회했으나 모두 빈 목록을 표시했다. Headless와 화면 표시 Chrome에서 재현했다. 사용자는 일반 브라우저에서 로그인 없이 열차 목록이 보인다고 확인했다. 따라서 이를 실제 운행 없음이나 매진으로 판정하지 않는다.

전용 프로필 Chrome을 열고 사용자의 수동 조회 결과와 비교 중이다. 실제 열차 행이 확보되기 전에는 selector를 추정하여 예약하지 않는다. 결과 로딩/오류 상태와 더보기 처리를 확인한 후 반복 조회를 연결해야 한다.

예약·카카오페이 요청/미결제/완료·발권 화면의 DOM, popup/iframe 구성, 정확한 문구와 예약 식별자는 아직 관찰하지 못했다. 엔진은 모의 사이트로 테스트했고 실사이트 거래 연결은 비활성화했다.

## 공개 조회 실패 진단 (추가)

사용자가 조건 차이와 무관하게 전용 브라우저에서만 목록이 비는 것을 확인했다. 이후 조건 비교를 중단하고 요청 상태를 조사했다.

- Playwright가 실행한 화면 표시 Chrome: 공개 조회 중 `www.korail.com/web_s/[동적 경로 생략]` XHR에서 HTTP 500. `Uncaught Error` 페이지 오류도 관찰. 해당 오류와 500의 인과관계는 아직 미확인.
- Chromium 보안 샌드박스를 활성화한 비교: 같은 HTTP 500 재현. 따라서 샌드박스 옵션 변경으로 해결되지 않음.
- 새 임시 프로필의 Chrome을 일반 프로세스로 실행한 후 공식 CDP 연결: 역시 HTTP 500. 이 실행에서는 최종 날짜가 요청한 날짜와 달라져 완전한 대조 실험으로 취급하지 않음. CDP 전환을 제품에 적용하지 않음.
- HTTP 500만으로 코레일의 자동화 차단이라고 확정할 수 없음. 새 프로필/세션 문제와 자동화 연결의 영향을 구분하기 위해 사용자의 일반 Chrome 시크릿 창 조회 여부를 요청함.

제품 개선: 공개 조회에서 HTTP 실패를 관찰하면 매진·운행 없음으로 취급하지 않고 별도 오류로 표시한다. 탐색 엔진에서는 설정한 오류 대기/배수/횟수 제한을 적용한다. 조회 클릭 후 관찰된 결과 요청 응답까지 기다려 초기 빈 컨테이너를 결과로 읽지 않도록 변경했다. 실제 행 렌더링 완료 조건은 행 구조 확보 후 추가 검증이 필요하다.

제품 진단에는 HTTP 상태 숫자·요청 실패 횟수·페이지 오류 횟수만 보관한다. URL, 쿠키, 헤더, 요청/응답 본문, 로그인·결제 화면은 보관하지 않는다. 개발 진단 도구는 로그인하지 않은 공개 페이지에서 경로·상태를 기록하되 query와 동적 경로를 생략한다.

## 느린 조작 비교

사용자의 속도 가설에 따라 기본 Chrome 실행 조건을 유지하고, 초기 화면 표시 후 10초 대기·각 클릭 후 2초 대기를 넣어 공개 조회를 한 번 실행했다. 동일한 HTTP 500이 재현되었다. 따라서 단순 클릭 간격 부족만으로 원인을 설명할 수 없으며, 자동화 차단 여부는 여전히 미확인이다.

신규 설정 기본값을 클릭 후 2초, 조회 화면 진입 후 10초로 두고 상세 설정에서 변경 가능하게 했다. 저장된 기존 클릭 간격은 덮어쓰지 않는다. 역 선택 직후 실제 입력값 반영도 확인한다. 초기 대기는 조회 화면을 새로 열 때마다 적용되며 조회 간격(이전 조회 완료부터 다음 조회까지)과 별개다.

## 오류 내용과 진입 경로 확인

- 페이지 오류 메시지는 `only one instance of babel-polyfill is allowed`이며, 발생 파일은 네이버 로그인 SDK `static.nid.naver.com/js/naveridlogin_js_sdk_2.0.2.js`였다. 이를 조회 실패의 원인으로 간주하지 않는다. 정상 Chrome에서 같은 오류가 발생하는지는 아직 확인하지 못했다.
- HTTP 500 HTML의 제목은 ‘코레일 승차권예매’, 화면용 안내 문구는 주소가 잘못 입력되었거나 변경/삭제되어 요청한 페이지를 찾을 수 없다는 내용이었다. 자동화 차단을 직접 명시한 응답은 관찰하지 못했다.
- 코레일 홈 `/ticket/main`을 먼저 열어 로드 완료 후 10초 기다리고 일반 조회 화면으로 이동한 실험에서도 같은 HTTP 500과 안내 문구가 재현됐다. 단순 홈 진입 초기화 누락 가설은 이 실험으로 뒷받침되지 않았다.
- 현재 연결 도구에는 정상 Chrome 탭이 노출되지 않아 작동하는 브라우저의 요청과 직접 비교할 수 없다. 사용자에게 일반 Chrome 시크릿 창에서의 수동 조회 결과를 요청했다. 기존 세션/프로필 영향과 자동화 환경의 영향을 구분하기 위한 다음 증거다.

진단 도구는 로그인하지 않은 새 프로필에서 페이지 오류 메시지·발생 파일과 실패 응답의 화면용 안내 문구를 추가로 수집한다. 동적 경로와 긴 토큰 문자열을 가리고 스크립트/스타일 및 응답 원문은 보관하지 않는다. 현재 조회 장애는 해결되지 않았으며, 새로운 확인 없이 자동화 관련 실행 플래그를 계속 바꾸지 않는다.

## 일반 Chrome 확장프로그램 검증으로 전환

- 사용자가 시크릿 Chrome에서도 비로그인 상태의 열차 목록이 정상적으로 표시된다고 답변했고 07:47/08:20 행이 보이는 스크린샷을 제공했다. 기존 로그인 쿠키가 반드시 필요한 현상은 아닌 것으로 보인다.
- 별도 프로필의 일반 Chrome을 0이 아닌 로컬 디버깅 포트로 실행하고 Playwright CDP 연결한 비교에서도 HTTP 500이 재현됐다. 이 방식은 제품에 적용하지 않았다. 재현 도구는 `tools/probe_normal_chrome.py`다.
- 사용자는 F12 진입 시 화면이 멈추고 JavaScript를 꺼도 진행되지 않는다고 보고했다. 개발자 도구 기반 비교 요청을 중단했다. 보호 동작의 정확한 원인은 확정하지 않았다.
- 사용자가 정상 브라우저의 확장프로그램 방식으로 접근하는 것을 승인했다. `extension/`에 activeTab+scripting 권한만 사용하는 읽기 전용 검증 버전을 만들었다.
- 확장프로그램은 현재 공개 목록 DOM을 읽어 텍스트와 제한된 구조만 보여주고 JSON으로 저장한다. 디버거·네트워크 감시·자동 클릭·외부 전송을 사용하지 않는다. 쿠키·숨김 입력·비공개 페이지는 읽지 않는다.
- 모의 DOM의 정보 범위/숨김 정보 제외/팝업/JSON 저장 검증은 `tools/smoke_extension.py`로 수행한다. 이는 실사이트 확장프로그램 성공 검증과 다르다. 사용자가 정상 Chrome에 설치한 후 실제 목록 읽기 결과를 받아야 다음 단계로 진행할 수 있다.

## 정상 Chrome 목록 읽기 성공 및 파서 연결

사용자가 `korail-public-snapshot-2026-10-01T04-37-30-165Z.json`을 제공했다. 2026-10-09 용산→정읍, 08:00 이후, 총 1명의 목록 10편이 읽혔고 `truncated: false`였다. 08:20의 411편은 일반실·특실 매진, 07:47편은 해당 로드 목록에 없었다. 이는 파일 시점의 표시 상태다.

실제 구조는 `.tckWrap > ul > li.tckList` 안에 `.info_inner`, `.num`, `.data_box h3.txt_bk`와 두 `.price_box`가 있는 형태다. `sold_out`은 매진, `gen`/`spe`와 등급·요금 표시는 일반실/특실, `yms`와 ‘입석 + 좌석’은 입석 포함으로 구분했다. `sold_out_soon`의 ‘특실(매진임박)’을 매진으로 오인하지 않는다. 신규 파서는 날짜·구간·열차번호·출발시각을 식별자로 묶고 경로 불일치·중복·잘린 데이터는 거절한다.

전체 10편 파싱과 그중 4가지 상태의 실제 공개 구조 fixture 테스트를 통과했다. 0.2 팝업은 관심 시각 표시와 ‘갱신 1회 시험’을 제공한다. 사용자가 버튼을 누를 때만 탭을 한 번 새로고침하고, 새 문서인지 및 기존 조회 조건 유지 여부를 확인한다. 대기시간은 1~120초로 설정한다.

## 2026-10-04 갱신 성공 및 반복 조회 구현

사용자 파일 `korail-public-snapshot-2026-10-04T06-32-02-766Z.json`은 `refreshProbe.status: success`, `status: readable`, `truncated: false`였다. 2026-10-09 08:00 용산→정읍 총 1명의 10편을 원본 구조에서 다시 파싱했다. 411편 08:20은 양 등급 매진, 457편은 입석 포함으로 지정석 후보에서 제외되었다. 07:47편은 현재 조회 시작 시각보다 앞서 목록에 없었다.

0.3은 같은 권한(activeTab/scripting)으로 별도 확장프로그램 설정창에서 반복 조회한다. 창이 살아 있는 동안에만 순차 갱신하며 탭별 Web Lock으로 중복 실행을 막는다. 일반실·특실 기본 허용, 선택 열차의 균등 선택 또는 선택적 선호 순서, 간격·재시도·종료 제한을 설정한다. 예약 클릭은 아직 없고 후보 발견 시 멈춘다. 모의 화면에서 횟수 제한·후보 발견·중지까지 확인했으며, 실제 반복 갱신은 사용자의 일반 Chrome에서 검증이 필요하다.

사용자가 후속 실행에서 “좌석이 없어서 그렇지 원하던 작업은 모두 잘 실행됐어”라고 확인했다. 이에 따라 0.3의 좌석 없는 상태에서 실제 반복 조회 흐름은 사용자 검증 완료로 기록한다. 각 설정 한계값, 실제 좌석 발견 시 정지, 예약 및 결제 성공까지 검증되었다는 의미는 아니다. 다음 확인 대상은 가격 셀 선택 전후의 공개 행 구조와 하단 예매 영역이다.

## 좌석 선택 상태와 할인 요금 (0.3.1)

사용자 파일 `korail-public-snapshot-2026-10-04T06-42-03-731Z.json` 및 동반 스크린샷은 2026-10-07 용산→정읍 05:48 403편 일반실 선택 상태다. 이는 화면 수집용 예시이며 예약 목표 날짜·열차 변경 요청으로 해석하지 않는다. 일반실 `.price_box`에 `active` 클래스가 붙는다. 할인형 가격은 `.txt_price`에 ‘15% 할인’, `.txt_gr`에 ‘29,700원’이 들어가 기존 파서가 가용 좌석을 놓쳤다. 할인 문구와 별도 금액을 검증하도록 수정했으며 해당 공개 행을 `korail-selected-discount.json`으로 축소 보관했다.

스크린샷에는 하단 예매 버튼이 있으나 기존 JSON의 `.tckWrap` 안에는 없다. 0.3.1 수집기는 공개 조회 페이지에서 정확히 ‘예매’, ‘좌석선택’, ‘운임요금’, ‘열차시각’인 보이는 버튼/링크의 태그·클래스·비활성 여부만 `actions`로 추가한다. 주변 계정 정보·링크 URL·이벤트 핸들러는 수집하지 않는다. 실제 버튼 정보의 새 수집은 아직 필요하며 자동 예약은 활성화하지 않았다. 파서 및 반복 제어 테스트 18개와 오프라인 Chrome smoke가 통과했다.

## 예매 후 분기 — 사용자 스크린샷 확인

후속 actions 발췌에서 활성화된 ‘예매’ 버튼이 두 개 확인됐다: `button.path_button`과 `button.btn_bn-blue02.reservbtn`. 후자는 하단 예매 버튼 후보이며 문구만으로 첫 버튼을 클릭하면 안 된다. 실제 클릭 연결은 아직 검증하지 않았다.

사용자가 다음 네 화면과 분기 설명을 제공했다. 로그인 입력값은 기록하지 않는다.

| --- | --- | --- |
| 선택 열차 이용안내 | `/ticket/search/list` | KTX-산천 2개 편성 연결 운행 안내가 나타날 수 있다. 이 안내가 실제 표시될 때만 그 안의 확인 버튼을 처리한다. 나타나지 않으면 기다리거나 억지로 클릭하지 않고 다음 화면을 판별한다. |

| 승차권 예약 | `/ticket/reservation/detail` | 날짜·구간·열차번호·시각·등급·좌석·결제기한을 확인한 뒤 대상 예약에 대해 결제하기로 진행한다. 이 화면은 발권 완료가 아닌 미결제 예약이다. |

스크린샷의 2026-10-07 05:48 403편은 수집용 예시로 유지하며 원래 목표 열차를 대체하지 않는다. 사용자가 확인한 정상 경로는 선택적 이용안내 → 예약 상세의 환불 안내 → 예약 상세다. 팝업이 반드시 표시된다는 가정 없이 현재 경로와 안내 종류로 분기한다. 알 수 없는 안내나 결과 불명확 상태에서는 예매를 반복하지 않고 확인을 요청한다.

현 단계는 화면 흐름에 대한 관찰 기록이며 자동 예매·로그인 후 재개·결제 연결이 구현 또는 실사이트 검증되었다는 뜻은 아니다. 공개 목록 수집기는 여전히 예약 상세와 로그인 화면을 읽지 않는다. 다음 관찰 대상은 결제하기 이후 결제수단 선택 화면의 경로와 카카오페이 선택 시 표시되는 화면이다.

## 결제수단 선택 및 카카오페이 별도 창

사용자가 결제 페이지 및 카카오페이 창 스크린샷 3개를 제공했다. 개인정보 입력값과 거래 URL의 식별자는 전사하지 않는다.

- 코레일 결제 페이지 경로는 `/ticket/payment/payment`다. 대상 열차·좌석과 금액을 표시한다. 대상 예약과 일치하는지 확인 후 간편결제 → 카카오 페이를 선택한다.
- 사용자 시연에서는 ‘코레일 앱(스마트티켓)으로 발권’ 및 ‘결제수단 저장’이 모두 체크되어 있다. 두 선택을 구현 시 명시적인 설정으로 다루며, 시연 화면을 근거로 필수 조건이라고 단정하지 않는다.
- ‘결제/발권’ 후 `online-payment.kakaopay.com`의 별도 Chrome 창이 열린다. 전체 URL은 거래 식별자를 포함하므로 수집·로그에서 제외한다.
- 카카오페이 창에는 QR결제와 카톡결제가 있다. 사용자 목표는 카톡결제이며 휴대폰번호와 생년월일 6자리 입력, ‘결제요청’ 버튼이 보인다. 이 단계는 휴대폰 결제 승인 전이다.
- 입력값은 채팅에서 다시 요청하거나 스크린샷에서 코드로 옮기지 않는다. 구현 시 사용자가 실행창에 입력하고 해당 실행 메모리에서만 쓰는 방식을 기본으로 삼는다. 로그·진단 JSON·소스·일반 설정 파일에 넣지 않는다.
- 코레일에서 결제창을 여는 제출과 카카오페이에서 메시지를 요청하는 제출을 별도 상태로 기록한다. 각 제출 전에 의도를 보존하고, 결과가 불명확하면 자동 재제출하지 않는다. 그 뒤 PC 완료 확인 동작만 사용자 설정 간격으로 반복한다.
- 현재 확장프로그램의 코레일 activeTab 권한으로는 다른 출처의 카카오페이 팝업 제어까지 보장되지 않는다. 팝업과 원래 탭의 연결, 필요한 해당 출처 접근 권한, 팝업 닫힘·차단·만료를 구현하고 검증해야 한다. 아직 권한 변경이나 자동 결제 동작은 적용하지 않았다.

다음 미확인 화면은 ‘결제요청’ 이후 PC의 대기/확인 화면, 휴대폰 승인 전 확인을 눌렀을 때의 미결제 안내, 실제 승인 후 발권 완료 화면이다. 요청 후 표시되는 제한시간을 읽고 예약 결제기한과 함께 적용해야 한다. 테스트 자료의 열차를 실제 구매 대상으로 자동 전환하지 않는다.

## 사용자 요청으로 카드 직접결제로 변경

후속 카드결제 스크린샷에서 `/ticket/payment/payment` 안의 개인카드 입력 폼과 ‘결제가 완료되었습니다.’ 안내를 확인했다. 사용자 시연에서는 별도 휴대폰 승인 없이 같은 페이지에서 결제 성공 안내가 나왔다. 다른 카드에서도 추가 인증이 없다고 단정하지 않는다. 카드번호·유효기간·인증번호·비밀번호 입력값은 이 기록에 전사하지 않는다.

필드는 카드번호 4개 구간, 유효기간 월/년, 인증번호(주민번호 앞 6자리), 할부개월, 비밀번호 앞 2자리, 개인정보 수집 및 이용동의다. 화면의 ‘결제수단 저장’ 설명은 개인정보 및 카드번호·비밀번호 등을 저장하지 않는다고 명시한다. 따라서 체크박스를 카드정보 보관 기능으로 해석하지 않는다.

앞선 카카오페이 대기 화면 요청은 더 이상 필요 없다. 새 구현 경로는 카드결제이며 결제 제출은 한 번, 불명확한 응답에는 재제출 대신 상태 확인을 적용한다. 결제 성공 안내와 최종 발권 확인을 분리한다. 다음 필요한 화면은 이미 성공한 결제 안내의 확인 버튼 이후 승차권 화면이다. 새 테스트 결제나 같은 예약 재결제는 필요 없다.

## 최종 승차권 확인 화면

사용자가 완료 화면으로 `/ticket/myticket/list`의 ‘승차권 확인’을 제공했다. 목록은 여러 날짜의 기존 승차권과 한 묶음 안의 여러 좌석을 포함할 수 있다. 따라서 URL 도착이나 목록 존재만으로 이번 작업을 완료 처리하면 안 된다.

완료 판정은 결제 성공 안내 이후 승차권 목록에서 이번 예약의 날짜·출발/도착역·열차번호·출발시각·등급·호차·좌석이 일치하는 발권 항목을 확인하는 방식으로 구현한다. 기존 목록에 이미 같은 대상이 있던 경우도 구분할 수 있도록 거래 전 상태 및 확보한 예약 식별 정보를 함께 대조한다. 대상 불일치나 확인 시간 초과 시 새 결제를 시도하지 않고 확인 필요 상태로 멈춘다.

현재 스크린샷에서 보이는 첫 승차권 묶음은 앞서 시연한 403편과 다른 열차다. 최종 페이지 형태는 확인됐지만 앞선 결제의 해당 승차권이 이 이미지 안에서 확인됐다고 기록하지 않는다. 승차권 번호와 QR/바코드 내용은 문서·fixture에 전사하지 않는다. 실제 DOM 구조와 자동 발권 검증은 여전히 구현·검증이 필요하다.

## 0.4 구현 및 검증

`booking-dom.js`는 관찰한 공개 목록 구조와 `.reservbtn` 버튼을 사용한다. 클릭 시점에 날짜·구간·시각·번호·등급·성인 조건 중 총 1명 표시·가격·선택 상태를 다시 확인한다. 총 1명 표시는 승객 유형까지 보장하지 않으므로 사용자가 성인 1명으로 조회해야 한다. 중복 열차·중복 버튼·가려진 버튼·매진·입석 상태면 제출하지 않는다.

`booking.js`는 선택 → 검증 → 거래 의도 저장 → 예매 1회 → 화면 판별로 연결된다. 응답 불명확, 로그인, 안내창, 예약 상세에서 정지한다. localStorage 기록과 확장프로그램 출처의 Web Lock으로 같은 프로필에서 중복 예매 요청을 막는다. 자동 재개/기록 삭제는 아직 제공하지 않는다.

설정창에 자동 예약 옵션과 별도 시간 설정 및 값 없는 단계 구조 진단을 추가했다. 실제 예약·결제 페이지의 필드 DOM은 미확인이라 카드 입력/제출과 완료 판별은 비활성 상태다. 모의 화면과 거래 테스트 24개, 두 Chrome smoke(목록/설정창 및 예약 DOM)가 통과했다. 사용자 브라우저에서 실예약이나 결제를 실행하지 않았다.

## 0.5 카드 입력 구조 연결

사용자가 `/ticket/payment/payment`에서 actions/fields/notices를 제공했다. 보이는 입력 요소 15개는 할인 select `sale_sel`, 개인/법인 radio `option01/option02`, 카드번호 text/password/password/text 네 칸, 월 text `mon03`, 연도 select, 인증 password `certi_num`, 할부 select, 비밀번호 password, 동의 checkbox `check`, 앱 발권 checkbox `shuttle01`, 결제수단 저장 checkbox `savePaymentMethod` 순서다. 입력값은 제공되지 않았고 저장하지 않는다.

`card-dom.js`는 이 구조를 전부 검증한 뒤 개인카드에 한해 네 번호 구간·유효기간·인증번호·비밀번호 및 일시불 옵션을 채운다. 설정된 동의/앱 발권 체크를 적용하고, 입력 이벤트 이후 값이 유지되는지 확인한다. 결과에는 성공 단계 또는 제한된 오류 코드만 반환한다. 구조가 다르면 입력하지 않는다. 입력 실패 시 민감 입력란을 지우도록 시도한다.

이 기능은 설정창에서 별도로 실행하는 입력 시험이며 자동 결제 제출은 제공하지 않는다. 예약 대조와 발권 항목 검증, 안내창 자동 처리 및 전 단계 자동 연결은 아직 남아 있다. 합성 카드 데이터의 모의 Chrome 페이지에서 정상 입력·입력란 변경·법인카드·입력 거부·잘못된 경로·미제출을 검증했다. 실사이트의 보안 입력 모듈은 미검증이다.

## 0.6 전체 실행 연결

사용자가 0.5 카드 입력은 잘 적용된다고 확인했으며, 한 번 입력 후 사용자 개입 없이 발권까지 진행해야 한다는 요구를 재확인했다. 이에 `checkout.js` 상태 흐름과 `checkout-dom.js` 의미 기반 페이지 어댑터를 추가했다. 시작 시 카드정보를 실행 메모리에 유지하고 입력 단계 및 제출 직전 재검증에서 재사용한다. 결제 의도 기록 후 실제 제출을 한 번만 수행하며 실패 시 다시 제출하지 않는다.

알려진 열차 안내·환불 안내·결제 성공 안내는 제목과 본문 및 해당 범위 내 유일한 확인 버튼을 대조한다. 예약 화면의 대상과 좌석·결제기한, 결제 화면의 대상과 1건 합계, 최종 목록의 대상 좌석을 대조한다. 예약/승차권 DOM은 아직 실제 구조 스냅샷이 없으므로 화면 문구와 제한된 컨테이너 범위로 보수적으로 구현했다. 불명확하면 중지한다. 구조 미확인을 실제 성공 검증으로 표현하지 않는다.

테스트 31개, 목록/설정창·예약 DOM·카드 입력·결제 흐름 DOM의 오프라인 검증을 수행했다. 설정창 모의 전체 실행에서 시작 한 번, 카드정보 재입력 없음, 결제 1회, 완료 후 카드값 정리 및 거래 기록에 카드정보 미포함을 확인했다. 실사이트 예약·결제는 도구로 실행하지 않았다.

## 0.6.1 선택 직후 안내 처리

사용자 스크린샷에 조회 화면의 ‘이용안내 / 서대전정차하는 열차입니다. 도착시간을 확인하시기 바랍니다.’와 실행 결과 `covered_action`이 표시됐다. 0.6은 예매 후에만 안내를 처리해 좌석 선택으로 열린 팝업이 예매 버튼을 가리는 경우를 놓쳤다. 선택 전후에도 조회 화면의 팝업을 처리하도록 수정했다. 서대전 안내와 확인 버튼만 있는 일반 이용안내를 지원하며 오류·매진·거래 관련 낯선 메시지는 제외한다. 팝업 반복 제한은 단계별로 적용한다.

선택 직후 안내 → 닫기 → 선택 검증 → 예매 흐름의 회귀 테스트 및 DOM 검증이 통과했다. 이전 `reservation_submitting` 기록에는 클릭 미실행 여부가 남지 않으므로 자동 삭제하지 않는다. 사용자가 실제 예약·승차권 내역을 확인한 경우에만 기록을 보관하고 실행 차단을 해제하는 복구 UI를 제공한다. 설정창 단순화는 사용자 요청대로 후속 작업으로 남긴다.

## 0.7 사용자 실행의 시간 초과 및 속도·보관함 변경

사용자가 팝업 하나를 넘긴 뒤 조회 화면에 남아 `transition_timeout`으로 정지한 스크린샷을 제공했다. 이것만으로 사이트의 예매 요청 수락 여부나 팝업 후 추가 클릭 필요 여부를 확정할 수 없다. 자동 재제출은 추가하지 않았다. 대신 단계별 대기 대상/현재 페이지, 팝업 처리, 예매 클릭 반환을 거래 기록에 남기고 시간 초과 코드를 세분화했다. 같은 팝업이 닫히는 동안에는 확인을 반복하지 않고 기다리도록 수정했다.

사용자 요청으로 조회 기본 0.7초, 선택 후 대기 0.1초, 페이지 확인 0.2초를 적용했다. 최근 60초 100회 제한은 확장프로그램 출처의 공유 잠금/저장 기록으로 매크로 재조회에 적용한다. 카드 보관함은 사용자 지정 비밀번호 기반 로컬 암호화를 사용하며 원본 카드값/비밀번호/키를 저장하지 않는다. 합성 데이터로 암호화/복원/잘못된 비밀번호/변조/삭제 및 조회 제한을 검증한다. 실사이트 시간 초과의 근본 원인은 새 실행 기록으로 확인해야 한다.

## 0.8 제공된 trace와 후속 요구

사용자가 제공한 trace는 조회 → route 안내 → 확인 → 조회 → reserve_click_returned → train 안내 → 확인 → 조회 순서다. 즉 예매 클릭 자체는 호출됐고 train 안내 이후 예약 화면으로 전환되지 않았다. 안내 뒤 추가 예매 클릭이 필요한 경로라는 가설을 반영해, 예매 이후 train 안내를 실제 처리한 경우만 동일 선택 확인/조회 화면 재확인 후 한 번 더 진행하는 분기를 추가했다. 이미 예약 화면으로 전환됐거나 안내 없이 시간 초과한 경우에는 재클릭하지 않는다. 이 분기의 실사이트 성공은 아직 미확인이다.

사용자가 개인정보 수집·이용동의와 앱 발권은 항상 체크하도록 명시했다. 카드 관리 별도 화면과 로컬 비암호화 저장도 요청했다. 이에 `cards.html/js`와 `card-store.js`로 카드 CRUD/저장을 분리하고 설정창의 입력 필드 및 동의/앱 옵션을 제거했다. 매크로는 시작 시 로컬 카드 스냅샷을 한 번 읽고 결제에 사용한다. 기존 보관함은 한 번 비밀번호로 복호화해 새 저장소로 옮길 수 있다. 원본 카드정보와 PIN 등은 소스·fixture·로그에 전사하지 않았다.

회귀 테스트 41개 통과. 모의 설정창/카드 탭에서 저장·편집·삭제·재로딩·설정창의 마스킹된 표시와 자동 결제 연결을 확인했다. 신규 분기는 안내 후 계속 진행, 안내 없는 재시도 금지, 최대 한 번 추가 클릭을 검증했다. 사용자 브라우저에서 실제 결제는 실행하지 않았다.


## 2026-10-04 v0.9: covered_action와 재시작

사용자 trace: route 안내 해제 → reserve 반환 → train 안내 해제 → continuing_after_train_notice에서 covered_action. 가림 원인이 애니메이션인지 스크롤인지는 확정하지 못했다. 즉시 스크롤과 명시적 pre-click covered 결과에 한정한 100ms/최대3초 준비 대기를 적용했다. 성공/통신 오류는 재시도하지 않는다. 지속 가림에는 구조만 기록한다.

자동 예약/결제 옵션과 수동 거래복구 UI를 제거했다. 전역 실행 잠금을 획득한 Start가 저널/화면 로그를 초기화한다. 카드와 rolling rate history는 유지한다. 중지→available 타깃 추가→재시작, malformed journal 초기화, route/train 연속 안내 뒤 가림, 지급 중복 방지를 오프라인으로 검증했다. 실제 예약/결제는 수행하지 않았다.


## 2026-10-04 v0.9.1: 예매 재클릭 가정 철회

사용자 로그에서 train 확인 후 약465ms 만에 reserve_continuation_returned, 이후221ms 만에 train 재등장/repeated_notice. 예매 재클릭이 필요한 흐름이라는 v0.8 가정은 검증되지 않았으며 재클릭으로 안내를 다시 연 가능성이 있다. 해당 분기를 제거하고 설정된 transitionTimeout 전체를 기다린다. 지연 전환 성공, 끝까지 조회 유지 시 1회 제출 후 timeout, 실제 안내 재등장 시 bounded stop 테스트를 반영했다. 실제 확인 버튼의 후속 동작이 왜 전환되지 않았는지는 아직 미확정이다.


## 2026-10-04 v0.9.2: 사용자 확인으로 안내 후 예매 진행 복구

사용자가 확인 버튼은 팝업만 닫고 예매 버튼을 눌러야 한다고 명확히 설명했다. 0.9.1에서는 확인 후 예매를 누르지 않는 문제가 확인됐다. train 안내 확인 후 선택을 재검증하고 조회 화면에 남아 있으면 예매를 진행한다. 그 명시적 클릭 후 seen notice 집합을 초기화해 같은 안내도 다시 확인한다. 전체 noticeCount와 단계 deadline은 초기화하지 않아 무한 루프를 막는다. 두 번의 train 안내를 확인한 뒤 예약/결제 완료하는 회귀 테스트, 8회 제한, 중지, 안내 없이 대기 시 재클릭 없음 등을 검증했다.


## 2026-10-04 v0.9.3: 반복 중단과 실제 클릭 대상 진단

사용자는 0.9.2가 안내창만 반복한다고 보고했다. 기존 코드가 button.reservbtn에 click()을 호출한 사실과 실제 파란 버튼의 정상 예약 처리는 구분해야 한다. 알려진 두 클래스와 텍스트로 대상을 좁히고 path_button을 배제했다. 클릭 반환에 target 구조를 추가했고 확인→예매 계속하기는 최대1회로 제한했다. 자동 클릭과 수동 클릭의 사이트 반응 차이는 아직 확인하지 못했다. 수정으로 실사이트 문제가 해결됐다고 주장하지 않는다.


## 2026-10-05 v0.9.5: 수동/자동 클릭 비교

제공된 trace에 파란 예매 버튼 클래스가 있고 reserve 호출 직후 train 안내가 발생한다. 예매 호출 자체와 사이트의 실제 예약 진행은 구분해야 한다. 확인 후 전환되지 않는 원인은 미확정이다. 클릭 횟수/속도 가정을 추가하는 대신 검색 페이지에서만 허용된 버튼의 passive event 기록을 추가했다. 입력값 없이 실제 이벤트와 synthetic click의 대상/순서를 비교하며 결제/로그인 페이지 이벤트는 기록하지 않는다. 기존 실사이트 실패는 해결됐다고 주장하지 않는다.


## 2026-10-05 v0.9.6: 실제 미결제 예약 존재

사용자 화면 `/ticket/reservation/list#`에 455편 07:43 미결제 1매 예약이 확인됐다. 생성 주체/정확한 시점과 새로고침 여부는 스크린샷만으로 확정할 수 없다. monitor는 found 후 return한 뒤 checkout을 await하므로 해당 루프의 동시 reload는 발견하지 못했다. 별도 popup 갱신 시험은 전역 실행 잠금이 없어 보완했다. 예약 전환 timeout 후 조회에 남으면 재클릭 대신 예약 목록으로 1회 이동해 정확한 대상 1매/기한을 검사한다. 목록에는 등급·호차·좌석이 보이지 않으므로 결제 화면의 상세정보로 보완한 뒤 카드결제에 진입한다. 모의 DOM/회귀로 검증했으며 실사이트 성공은 미확인이다.


## 2026-10-05 v0.10.0: 현재 선택 1건에 집중

사용자가 반복조회보다 재고 있는 1건의 정상 흐름을 먼저 검증하자고 요청했다. 웹페이지의 active 가격 셀 하나를 엄격히 읽는 단일 실행 경로를 추가했다. 반복조회 설정을 사용하지 않으며 reload/recovery navigation을 호출하지 않는 UI 테스트를 추가했다. 직접 클릭 기록의 마지막 경로가 payment였으므로 정상 안내 후 결제 화면 직행도 허용하되 대상/단일건/좌석을 검증한다. 안내 클릭 전 대기와 단계 간 대기를 0.8초(설정가능)로 시험한다. 이는 성공 원인 확정이 아니며 라이브 검증이 남았다.
