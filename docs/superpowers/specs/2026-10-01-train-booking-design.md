# 개인용 기차 예약 프로그램 설계

작성일: 2026-10-01
상태: 대화에서 합의한 설계를 문서화함. 문서 최종 검토 단계.
기준: 루트 기획서 v0.5와 이후 사용자 승인. 구현 시 충돌하는 과거 초안보다 이 문서를 우선한다.

## 1. 목표와 범위

Windows에서 작은 설정창과 Playwright 전용 브라우저를 사용한다. 사용자는 시작할 때 로그인·여행 조건을 설정한다. 프로그램은 지정한 열차들을 감시해 한 편을 예약하고 카카오페이 결제를 요청한다. 사용자는 휴대폰에서 금액을 확인하고 결제한다. 프로그램이 PC의 완료 확인을 반복하여 결제·발권 확인까지 마무리한다.

첫 버전은 개인 한 계정, 편도 한 날짜·한 구간, 성인 1명, 총 예약 1건이다. 다른 승객 유형이나 여러 명을 선택하는 기능은 첫 버전에 노출하지 않는다. 여러 목표 열차, 일반실·특실 허용 설정, 선택적인 열차 선호 순서, 변경 가능한 속도·재시도 설정을 지원한다.

카카오페이 외 결제수단, 별도 메신저 알림, 자동 취소·환불, 입석·예약대기 신청, 여러 계정·병렬 예약은 범위에 포함하지 않는다. 금액 상한은 두지 않으며 사용자가 카카오페이에서 직접 확인한다.

## 2. 사용자 흐름

1. 설정창에서 브라우저 열기를 누른다. 자동화 전용 브라우저에서 직접 코레일에 로그인한다.
2. 탑승일·출발역·도착역을 설정하고 열차를 조회한다. 목록에서 감시할 열차를 여러 개 선택한다. 열차번호는 결과에서 연결한다.
3. 허용 등급·선호 순서·조회간격을 설정하고 시작한다. 상세 시간 설정은 접힌 영역에서 변경한다.
4. 현재 상태, 목표별 좌석 상태, 마지막 조회 시각, 다음 조회까지 남은 시간, 누적 조회 횟수를 확인한다.
5. 좌석이 확보되면 탐색을 중지하고 해당 예약으로 카카오페이 요청을 한 번 보낸다.
6. 사용자가 휴대폰 메시지를 열어 금액 확인·결제를 한다. PC 조작은 정상 경로에서 요구하지 않는다.
7. PC가 완료 확인을 반복하고 발권 내역을 검증한다. 설정창에 열차·좌석·결제·발권 결과를 표시한다.

브라우저는 실행 결과 확인을 위해 완료 후에도 유지한다. 설정창 종료는 새 작업을 중단하며 예약이나 결제를 취소하지 않는다. PC 절전·브라우저 종료 중에는 감시가 지속되지 않는다.

## 3. 설정

### 여행 조건

| 항목 | 기본값 / 동작 |
|---|---|
| 탑승일·역 | 실행 시 사용자 지정; 지난 날짜는 시작 불가 |
| 대상 열차 | 조회 결과에서 하나 이상 선택; 시각·번호·구간으로 식별 |
| 승객 | 성인 1명으로 표시 |
| 좌석 등급 | 일반실·특실 모두 기본 선택; 한쪽만 허용 가능; 모두 해제 불가 |
| 열차 선호 순서 | 기본 없음; 사용 시 선택한 열차 전체 순서 지정 |
| 결제수단 | 카카오페이 |
| 금액 상한 | 입력·검사 없음 |

일반실과 특실 중 실제 가능한 허용 등급이 있으면 해당 열차를 후보로 삼는다. 열차 선호 순서가 없을 때 가능한 열차 중 균등 무작위로 한 편을 선택한다. 그 열차에서 두 등급이 모두 가능하면 등급도 균등 무작위로 선택한다. 두 등급이 가능한 열차의 가중치를 두 배로 높이지 않는다. 선호 순서 사용 시 가능한 열차 중 가장 우선인 것을 선택한다. 우선 열차가 매진이라고 다른 가능한 후보를 기다리지 않는다.

### 속도·대기·종료

모든 아래 수치는 설정값이며 코드에 고정하지 않는다. 단위는 화면에 명시한다.

| 설정 | 기본값 | 의미 |
|---|---|---|
| 조회간격 | 10초 | 조회·대상 판별 종료부터 다음 조회까지; 소수 지원 |
| 화면 전환 제한시간 | 30초 | 페이지 전환의 최대 대기 |
| 요소 준비 제한시간 | 10초 | 목록·버튼 준비의 최대 대기 |
| 동작 사이 추가 대기 | 0초 | 요소 준비 후 추가 지연 |
| 명확한 예약 실패 후 대기 | 10초 | 예약 실패 확정 후 재조회까지 |
| 조회 오류 첫 대기 | 20초 | 첫 오류 후 재시도 대기 |
| 오류 대기 배율 | 2 | 1이면 일정한 대기 |
| 오류 대기 상한 | 80초 | 증가 대기의 최대값 |
| 연속 오류 허용 횟수 | 3회 | 해당 오류 횟수 도달 시 일시정지 |
| 최대 조회 횟수 | 제한 없음 | 최초 조회와 오류 재시도 요청 포함 |
| 최대 실행시간 | 2시간 | 탐색 시작부터 경과시간, 일시정지 포함; 제한 없음 가능 |
| 종료 시각 | 없음 | 한국시간 날짜·시각 지정 가능 |
| 결제 상태 확인 간격 | 3초 | 확인 응답·미결제 안내 닫기 종료부터 다음 확인까지 |
| 휴대폰 결제 최대 대기 | 10분 | 프로그램의 최대 대기이며 서비스 기한을 연장하지 않음 |
| 발권 확인 제한시간 | 60초 | 승인·완료 응답 후 발권 확인의 최대 대기 |

간격과 제한시간은 양수, 추가 대기는 0 이상, 배율은 1 이상, 오류 대기 상한은 첫 대기 이상이다. 횟수는 양의 정수이며 최대 조회 횟수와 최대 실행시간은 명시적 ‘제한 없음’을 지원한다. 화면·요소 대기는 최대시간으로, 준비가 완료되면 즉시 진행한다.

연속 n회째 조회 오류의 대기는 `min(첫 대기 × 배율^(n-1), 상한)`이다. 오류 허용 횟수에 도달하면 새 재시도를 만들지 않는다. 정상 조회 시 오류 횟수를 초기화한다. 매진과 결제 미완료 안내는 오류가 아니다. 사이트가 대기를 지정하면 그 시간을 우선한다.

여러 탐색 종료 조건은 가장 먼저 충족하는 것을 적용한다. 모든 목표 열차가 출발해도 종료한다. 예약을 확보한 뒤에는 탐색 한도 대신 결제 단계의 기한을 적용한다.

탐색 중 속도 변경은 다음 대기·작업부터 적용하며 진행 중인 요청의 제한시간을 변경하지 않는다. 대기 중 조회간격 변경은 마지막 조회 완료 시점과 새 간격으로 남은 시간을 다시 계산한다. 이미 새 간격이 경과했다면 현재 요청이 없는 상태에서 다음 조회를 시작한다. 예약·결제 처리 중에는 설정을 잠근다.

## 4. 구성요소와 경계

구현 기술은 Python, Tkinter 기반 설정창, Playwright의 화면이 보이는 브라우저로 정한다. 브라우저 종류와 실행 호환성은 첫 기술 검증에서 확인한다. 별도 웹 서버나 데이터베이스 서버는 두지 않는다.

| 구성요소 | 입력·출력 | 책임 |
|---|---|---|
| 설정창 | 설정·실행 명령 → 작업 큐, 상태 이벤트 → 표시 | 사용자 입력과 진행 상태 |
| 실행 제어 | 명령·화면 결과 → 상태 전환·다음 작업 | 한 번에 하나의 자동화 작업, 대기·중지·재개 |
| 목표 선택 | 설정·열차 목록 → 예약 후보 | 날짜·역·번호·등급 일치 및 선호 정책 |
| 사이트 처리 | 조회/예약/결제 확인 명령 → 정규화된 결과 | 실제 화면 식별·클릭·내용 읽기 |
| 상태 저장 | 실행·거래 상태 → 로컬 기록, 기록 → 복구 정보 | 요청 전 기록, 재시작 시 대조 |

GUI는 주 스레드, Playwright는 하나의 작업 스레드에서 소유한다. GUI가 Playwright 객체를 직접 조작하지 않는다. 명령과 상태 이벤트는 큐로 전달한다. 대기 중에도 중지 요청을 받을 수 있게 하며, 진행 중인 웹 동작은 설정한 제한시간 내에서 종료·응답 확인한다.

사이트 처리 결과는 가능·매진·예약대기·미발견·로그인 필요·알 수 없는 화면을 구분한다. 화면 밖 더보기를 포함해 목표를 읽고 검색 조건이 유지되는지 확인한다. 알 수 없는 화면을 매진으로 취급하지 않는다.

## 5. 상태 전환

정상 경로: 준비 → 로그인 대기 → 탐색 → 예약 제출 → 예약 검증 → 결제 요청 → 휴대폰 결제 대기 → 발권 확인 → 완료.

예외 상태: 일시정지, 거래 결과 불명확, 만료, 취소, 중지. 상태 이름과 원인을 설정창에 표시한다.

- 조회 중 매진: 설정 간격 후 다시 조회한다.
- 예약 실패가 명확함: 설정한 실패 대기 후 탐색으로 돌아간다.
- 예약 응답이 불명확함: 기존 예약을 확인하기 전 재제출하지 않는다.
- 로그인 만료: 일시정지하고 사용자가 로그인한 뒤 재개한다.
- 새로운 팝업: 진행을 멈추고 확인 필요 상태로 둔다.
- 중지: 새 조회·클릭을 막는다. 이미 제출된 거래의 결과 확인은 수행한다.
- 한 편 확보 후: 다른 후보 탐색을 시작하지 않는다. 결제 실패나 미응답도 새 예약의 근거가 되지 않는다.

예약 성공은 대상 날짜·구간·열차·인원·허용 등급과 배정 좌석, 미결제 상태를 확인한 경우다. URL이나 버튼 이름 하나만으로 성공 처리하지 않는다.

## 6. 카카오페이 완료 확인

사용자 설명에 따른 절차:

1. 목표 예약을 확인하고 카카오페이 요청을 한 번 보낸다.
2. PC의 ‘결제 완료 후 확인’ 버튼을 누르고 결과를 기다린다.
3. 알려진 미결제 안내이면 그 안내창의 확인 버튼을 닫는다. 설정 간격 후 2번으로 돌아간다.
4. 완료 응답이면 확인 반복을 멈추고 해당 거래의 결제·발권 내역을 검증한다.

결제 화면과 안내창의 두 확인 버튼을 각 화면 문맥으로 구분한다. 확인 응답을 기다리는 동안 다음 클릭을 시작하지 않는다. 미결제 안내의 정확한 문구와 화면 구조는 초기 실사이트 검증에서 확인한다. 알려지지 않은 오류 안내는 자동으로 닫고 반복하지 않는다.

사용자가 설명한 서비스 제한은 10분이다. 화면에서 실제 카운트다운·만료시각을 읽을 수 있으면 그것을 우선한다. 읽지 못하면 요청 시작부터 10분을 사용자 설명에 근거한 임시 기준으로 사용한다. 설정한 프로그램 대기, 서비스 기한, 예약 결제기한 중 먼저 도래하는 시각까지 확인한다. 재시도나 재시작으로 기한을 초기화하지 않는다.

기한에 도달하면 새 확인 반복은 멈춘다. 이미 전송된 확인의 응답과 구매·발권 내역을 확인하여 경계 시점에 결제된 거래를 실패로 오인하지 않는다. 결제 승인만 확인되고 발권이 불명확하면 발권 확인 상태를 유지하며 제한시간 초과 시 결과 불명확으로 종료한다. 새 결제를 요청하지 않는다.

카카오페이 요청에 수신자 정보가 필요한지는 실제 화면에서 확인하고, 요구하는 필드만 프로그램에서 입력받는다. 휴대폰 비밀번호·인증값은 수집하지 않는다.

## 7. 상태 보관과 복구

설정, 로그인 프로필, 실행 상태는 OneDrive 프로젝트 밖의 로컬 사용자 앱 데이터 디렉터리에 보관한다. 개발 중 해당 경로 쓰기는 실행 환경 권한에 따라 처리한다. 비밀번호·결제 인증값은 저장하지 않는다. 로그에는 세션 쿠키·결제 수신자 정보를 넣지 않고 결제 화면의 스크린샷·트레이스·영상도 기본 수집하지 않는다.

실행 ID, 목표 조건, 실행 전 기존 예약 기준 정보, 현재 단계, 예약 식별정보, 결제 요청 시작시각, 거래 기한, 마지막 확인 결과를 보관한다. 거래를 만드는 동작 전에 기록을 원자적으로 저장하고 저장 실패 시 제출하지 않는다. 프로그램을 중복 실행해도 같은 프로필·실행 상태를 동시에 조작하지 못하도록 실행 잠금을 둔다.

재시작 시 저장된 단계와 실제 예약·구매 내역을 대조한다. 프로그램이 만든 미결제 건을 명확히 식별하면 상태 확인부터 재개한다. 이미 결제·발권 완료이면 완료로 표시한다. 동일 목표의 기존 예약이 있으나 이번 실행의 건인지 알 수 없으면 추가 예약을 막고 사용자가 대상을 확인하게 한다. 상태 파일만 믿고 새 거래를 만들지 않는다.

## 8. 검증과 완료 기준

처음에 실제 화면의 로그인·조회 갱신·더보기·예약 안내·카카오페이 입력·미결제 안내·완료 내역을 확인한다. 검증되지 않은 selector나 응답 문구를 추측해 실제 예약을 실행하지 않는다. 아직 확인하지 못한 결제 화면은 구현 완료로 보고하지 않는다.

모의 화면과 상태 제어 테스트로 다음을 검증한다.

- 목표 날짜·구간·번호가 다르면 예약하지 않는다.
- 등급 필터와 선호 순서가 반영되고, 기본 열차 가중치는 동일하다.
- 조회간격·재시도·종료 조건 변경이 동작에 반영된다.
- 예약 선점 실패와 예약 결과 불명확을 구분한다.
- 반복 미결제 안내에도 결제 요청은 한 번이며 정상 대기를 유지한다.
- 결제 성공 시 확인 반복을 종료하고 발권을 확인한다.
- 요청 후 중지·시간 초과·브라우저 종료·재시작이 중복 거래를 만들지 않는다.
- 결제기한 경계에서 완료된 거래를 단순 실패로 처리하지 않는다.

설정창은 열기·로그인·목표 선택·조회간격 변경·일시정지·중지·오류 표시를 직접 확인한다. 마지막 실사이트 검증은 사용자가 실제 원하는 한 건을 대상으로 수행한다. 테스트 목적으로 임의 열차를 반복 예약·결제·취소하지 않는다.

최종 완료 기준은 작은 설정창에서 실행해 목표 예약 한 건을 확보하고, 사용자의 휴대폰 결제 후 추가 PC 조작 없이 해당 예약의 결제·발권을 확인하는 것이다. 실제 화면 확인이 필요한 항목은 개발 첫 단계의 조사 작업이며 추가 제품 기능 결정이 아니다.

## 9. 다음 단계

이 문서 검토 후 구현 계획을 작성한다. 순서는 실행 환경·실사이트 조사, 설정과 선택 정책, 실행 상태와 복구, 예약·결제 처리, GUI 통합, 모의 및 실사이트 검증이다. 실제 사이트 조사 결과가 설계와 다르면 그 근거를 기록하고 영향을 받는 부분만 수정한다.
